# aether-application

Aether 边缘内核中与传输无关的命令和查询用例。

`EdgeApplication` 由 CLI、MCP 和可选的网络传输共用。它对点位读取做授权、校验设备命令、要求必须有审计接收器，并通过能力端口下发控制。基础设施的选择留在此 crate 之外，因此它的默认依赖图不包含 Redis、PostgreSQL、SQLx、MQTT 客户端或 Web 框架。

控制、手动执行规则、规则与告警策略变更、告警解除、I/O 通道投运以及物理动作路由变更，都会在调用非幂等端口之前先持久化一条 `Attempted` 审计事件。通道审计详情会标明被修改的字段，但绝不包含协议参数或各通道的日志设置值。如果执行前的事件无法存储，执行将失败关闭。端口一旦接受了操作，若终态的 `Succeeded` 事件追加失败，返回的是带有 `CompletionAuditStatus::Incomplete`、请求与命令/规则关联 ID 且 `is_retryable() == false` 的 `AcceptedOutcome`；它绝不会被转成可重试错误，从而导致同一操作执行两次。审计详情包含与具体操作相关的命令目标、规则标识符、动作数量或路由键。

`DataProcessingApplication` 是 Aether 数据处理的与传输无关的查询外观。组合根注册一个声明式任务、一个 `DataProcessingBinding` 和一条 `DataProcessor` 路由。绑定把任务内的测量名称解析为只读的 `PointAddress` 值，并可以固定静态特征和工件选择器；API 调用方永远无法选择处理器路由。

已经落地的外部绑定是 `aether-api` 中带认证的 `/api/v1/data-processing/*` HTTP 接口。版本 1 没有实现数据处理的 CLI 和 MCP 绑定。

对每个处理请求，应用先授权再读取数据，查询有界的历史数据和协变量，仅对使用 `Last` 聚合的特征可选地合并一段精确对齐的只读实时尾部，组装出每个特征各有一条出处条目的完整帧，计算共享的规范摘要，施加精确的帧和载荷上限，并把处理器的响应视为不可信。只有关联正确且符合策略的结果才会成为 `DerivedData`。该外观没有 SHM 写入器、历史接收器或命令分发器，路由集为空仍然是有效的默认配置。传输层的请求 ID 和结果 ID 是稳定的 UUIDv5 派生值，调用方原始的请求 ID 则保留在审计记录中。该查询是非幂等的：内容相同的重复请求可以保持稳定的关联 ID，但每次调用仍会执行处理器并写入必需的审计。

应用限定的是来源事件时间；适配器没有提供的时间先后关系，它无法凭空构造。在当前的 SQLite 表结构和工件选择器下，一个较早的 `as_of` 并不能证明存在按摄取时间/来源纪元或按模型可用时间划定的截面。历史评估必须提供冻结的输入，或者提供其契约携带并校验这些截面的端口。

```bash
cargo test -p aether-application
```
