# 数据处理流程

Aether 使用请求驱动的数据处理路径。`DataProcessingApplication` 组装一个完整、时间有界的 `ProcessingFrame`，并把它发送给选定的 `DataProcessor`。处理器绝不会先收到一个站点标识符，再回调 SHM、历史或配置去发现自己的输入。**由数据方请求处理器；处理器不请求 Aether 的数据。**

这条路径在设备数据完成解码并发布之后才开始。它始终位于 SHM 写入路径、历史持久化、规则和告警热路径以及命令交付之外。版本 1 提供一个带认证的 HTTP 查询；未来的定时规划周期必须使用同一个边界。它的失败不能使设备轮询、实时状态发布、确定性保护、告警或现有的控制行为停止。

## 端到端路径

```
Caller: authenticated HTTP / in-process application work
                            │
                            ▼
               DataProcessingApplication
                 │ resolve task, binding,
                 │ processor policy, as_of
                 │
        ┌────────┼───────────────┐
        │        │               │
        ▼        ▼               ▼
  HistoryQuery LiveState   CovariateSource
  historical  current SHM  weather / calendar /
  observations Last-only   schedule / tariff
               live tail
        │        │               │
        └────────┼───────────────┘
                 ▼
         ProcessingFrame assembler
          align / aggregate / validate /
          quality-policy / digest
                 │
                 ▼ complete, bounded request
            DataProcessor
        local algorithm / model sidecar /
               remote service
                 │
                 ▼
      ProcessingResult validation
                 │
                 ▼
       authenticated HTTP response
                 │ future separate use case
                 ▼
              planner
                 │ constraints and policy
                 ▼
       ControlApplication → SHM + UDS → IO
```

上半部分是查询和派生数据路径。下半部分的控制路径只有在另一个独立的应用决策之后才开始。`DataProcessor` 不持有 `LiveStateWriter`、动作分发器、告警生命周期、规划器或协议适配器的任何引用。

## 1. 从显式的任务请求开始

调用方选择的是一个已启用的 `DataProcessingTask`，而不是任意的站点点位、处理器 URL 或模型文件。请求至少要标明：

- 任务和任务契约版本；
- 任务运行所在的已投运绑定；
- 调用方/请求上下文和有界的截止时间；
- 一个稳定的 `as_of` 时间戳；
- 与任务相关的参数，例如预测范围；
- 与任务相关的带类型选项。处理器路由和制品策略从已投运的配置中解析，绝不由调用方选择。

`as_of` 冻结帧的事件时间截面。晚于该截面的历史观测和实时观测会被排除。外部预测或排程记录的是在该截面时可用的版本。这可以防止这些来源越过它们声明的时间边界；但它并不是 API 重放保证，在当前的历史库和制品元数据条件下，也不能证明离线回测不泄漏未来信息。

应用为整个请求解析同一个配置修订：任务结构定义、站点绑定、单位和符号规则、时间策略、质量限制、处理器和出口策略都不能在帧组装的中途发生变化。配置在 `aether sync` 之后沿 Aether 的正常路径生效；运行时服务不直接解析行业包的 YAML。

## 2. 查询历史窗口

`HistoryQuery` 为任务所绑定的观测字段提供有界的回看窗口。它是一项领域能力，而不是数据库抽象。`DataProcessingApplication` 和 `DataProcessor` 既看不到 SQL，也看不到与存储相关的序列键。

默认的生产适配器以只读/仅查询模式惰性打开现有的 `aether-history.db`。它不创建或迁移历史库的表结构。一次逻辑请求中的每个特征读取都共享一个 SQLite 事务，因而共享同一个快照。对于节奏 `c`，历史标签在 `as_of` 处结束；标签 `t` 使用该特征已投运的聚合策略和重复数据策略，对 `(t-c, t]` 内的原始观测进行归约。空桶保持缺失，来源水位线是实际参与的最新一条原始数值行，而不是 `t`。

表结构迁移、写入、保留和文件生命周期只归 `aether-history` 所有。查询适配器依赖 SQLite 的快照/WAL 语义和读取权限。如果文件暂时不存在或无法访问，只有这次处理请求会变成带类型的不可用；它的惰性读取器可以在之后的调用中恢复。不会悄悄换用外部历史库。

生产环境的权限必须让这种所有权在物理上成立：API 得到一个专用的只读历史数据库/WAL/SHM 目录或只读身份，并与其可写的配置/审计数据库分开。在基础的共享 `/app/data:rw` 挂载上设置 SQLite 只读标志并不能提供这条边界。

读事务是请求运行时数据库的快照，而不是数据库在历史 `as_of` 时刻内容的快照。行中没有摄取时间，也没有来源/配置纪元。因此，带有较早事件时间戳的迟到修正可能出现在之后的重放中，而隐藏在同一个逻辑 `(series_key, point_id)` 背后的物理重新映射可能把新旧来源纪元拼接起来。预期的任务/绑定修订号只守护当前配置；它们无法过滤历史行中不存在的元数据。离线评估应使用冻结的数据库/导出，或者在声称具备时间点可复现性之前，先增加带纪元的双时态 `HistoryQuery`。

运行时的 SQLite 权威性守卫会把路由与持久化的 `history_config.storage_*` 进行比较。这些设置是已保存的意图：`PUT /hisApi/storage` 不会让活动的写入器重新连接。应把任何存储变更都当作一次维护边界：禁用处理，重新连接或重启历史服务，验证一条预期的哨兵序列，然后重启 `aether-api`，这样读取器就不会连到一个与活动写入路径不同的配置路径上。

可选的 HTTP 历史适配器只用于已经物化出确切节奏网格的环回上游。它支持 `last/reject`，不支持原始数据聚合。处理器永远得不到数据库或历史 API 的访问权限。

## 3. 应用当前的实时尾部

持久化的历史可能比当前设备值滞后一个采样间隔或刷盘间隔。`DataProcessingApplication` 通过只读的 `LiveState` 端口只读取任务所需的点位，并且可以为显式映射的特征替换对应的最后一个区间单元。不完整的实时尾部只改变这些被映射的单元；无关的历史特征保留其存储的值和出处。

只有当该特征已投运的历史聚合为 `Last` 时，这样做才有效。SHM 的瞬时值无法代表 `Mean`、`Sum`、`Min` 或 `Max` 桶，因此 v1 对这些策略拒绝 `live_tail: true`。能源负荷任务和光伏任务的目标都使用 `Mean`，因此禁止实时尾部。

SHM 仍是当前 T/S 状态的权威。实时读取不是第二个历史库，它只贡献可用的当前样本及其来源时间戳。帧组装器会：

1. 拒绝未写入、非有限、来自未来或超龄的实时值；
2. 把被接受的样本只映射到该特征的最后一个区间末单元；
3. 对重叠部分遵循任务显式的来源权威规则，而不是任意的“后写者胜出”行为；
4. 记录最后一个区间来自历史、实时状态还是两者兼有；
5. 保留缺失状态，而不是悄悄用零代替。

处理器不会映射 SHM，不理解槽或写入器代次，也不会得到 `LiveStateWriter`。这把共享内存 ABI 留在 Aether 内部，并保持 IO 对 T/S 写入的独占所有权。

SHM v5 为实时值保留源自设备的质量，API 把这个来源质量与自己的新鲜度策略结合起来。当前的 SQLite 历史表结构仍然只存储数值观测而不带来源质量。版本 1 会强制检查新鲜度、间隙、缺失、数值约束、出处和发布时间，但如果部署要求历史特征带有原始质量，就必须提供带质量信息的历史适配器。

## 4. 解析协变量和上下文

有些任务需要的数据并不是设备观测。预测可能用到未来天气、日历字段、电价、已知设定值或生产排程。配置的 `CovariateSource` 只返回任务声明的字段。

每个协变量都携带事件时间和来源出处。预测类协变量还携带发布时间或版本，使组装过程选取的是在 `as_of` 时可用的那份预测，而不是之后修正过的预测。这只封住了协变量版本这一条边界；历史截面和模型制品截面仍有上文所述的各自限制。确定性的日历字段可以按任务声明的时区策略在本地生成。

必需字段和可选字段是显式区分的。如果缺少必需的协变量，帧就不可用，除非任务声明了特定的回退。不能仅仅因为处理器接受一个数字，就悄悄用过期的值向前填充。

## 5. 组装 ProcessingFrame

应用把来自各个来源的样本组装成一个与处理器无关的 `ProcessingFrame`。概念上的预测帧如下所示：

```json
{
  "schema": "aether.processing-frame.v1",
  "as_of": "2026-07-11T12:00:00Z",
  "cadence_seconds": 900,
  "history": {
    "timestamps": ["2026-07-11T11:45:00Z", "2026-07-11T12:00:00Z"],
    "features": {
      "load": {
        "value_type": "number",
        "unit": "kW",
        "values": [820.0, 835.0],
        "quality": ["good", "good"]
      }
    }
  },
  "future_covariates": {
    "timestamps": ["2026-07-11T12:15:00Z", "2026-07-11T12:30:00Z"],
    "features": {
      "temperature": {
        "value_type": "number",
        "unit": "Cel",
        "values": [32.1, 32.0],
        "quality": ["good", "good"]
      }
    }
  },
  "static_features": {},
  "quality": {
    "input_watermark": "2026-07-11T11:59:58Z",
    "missing_ratio": 0.0,
    "max_gap_seconds": 900,
    "live_tail_included": false,
    "substituted_samples": 0
  },
  "provenance": [
    {
      "segment": "history",
      "feature": "load",
      "source_kind": "history",
      "source_ref": "energy.site.load.active_power",
      "watermark": "2026-07-11T11:59:58Z"
    }
  ]
}
```

线上编解码可以是 JSON、CBOR 或其他带版本的表示；语义契约保持不变。具名、带类型的字段使 Aether 不依赖私有的算法名称或张量名称，也使请求可以被检查，并可用于离线一致性测试夹具。

Aether 一侧的应用负责与站点数据语义相关的工作：

- 解析实例和点位绑定；
- 按 UTC 对时间戳排序，并应用声明的本地时间策略；
- 校验已投运的单位、比例、偏移、点位类型和目标符号已经与任务相符（v1 不执行运行时的单位/符号转换）；
- 应用任务声明的聚合和重采样规则；
- 把字段对齐到共同的时间网格，并保留缺失掩码；
- 检查回看窗口、新鲜度、时钟偏差、间隙和完整性要求；
- 派生任务声明的、与处理器无关的字段；
- 记录来源水位线和出处。

处理器负责与其实现或制品相关的工作：

- 选择配置的算法或允许的模型制品；
- 按该实现的要求排列具名字段；
- 与算法相关的变换、缩放和张量构造；
- 执行确定性库、本地模型或远程端点；
- 对输出做逆变换，并报告实现出处。

这种划分使设备和点位语义不进入处理器，私有的算法表示不进入 Aether 内核。

校验之后，应用针对带版本的任务身份、带版本的绑定身份、处理器契约、可选的制品选择器、归一化的帧（包括 `as_of`）和带类型的选项，计算一个规范的输入摘要。处理器端点、请求 ID、提交时间和截止时间不是摘要的输入。因此，对完全相同的归一化受治理内容的独立调用会得到相同的摘要；当数据源可变时，仅仅重复 `as_of` 并不能保证内容相同。版本 1 不使用该摘要做重放或去重。

制品选择器的版本和摘要标识所使用的字节。版本 1 不携带制品的 `trained_through` 或 `available_at`，因此为一个较早的 `as_of` 选用当前固定的模型，仍可能引入模型版本上的信息泄漏。在这些元数据成为投运和校验的一部分之前，历史模型评估必须使用在外部冻结的制品注册表/截面。

## 6. 调用 DataProcessor

`DataProcessingApplication` 通过 `DataProcessor` 端口发送完整的帧、输入摘要、请求 ID、截止时间、带类型的输出契约和处理器选择策略。适配器可以调用：

- 进程内的确定性算法；
- 同一台边缘主机上以边车形式运行的模型端点；
- 单独受监管的本地处理服务；
- 显式配置的远程处理 API。

模型端点只是一种请求驱动的处理器。它在请求中收到具名的观测和协变量，并且可以拥有模型制品、特征排序、缩放、张量构造和执行。它不会先收到一个 `plant_id`，再去查询 InfluxDB、Aether 历史、SHM 或站点配置。

处理器无论位于何处，都实现同一个端口并收到同样的受治理帧。位置不会改变数据权威，也不会授予访问任意 Aether 状态的权限。

调用受到载荷、并发和截止时间限制的约束。`data_processing.process` 是非幂等的：v1 没有重放存储或去重契约，再次调用可能再次执行处理器工作。调用方只在自己有界的策略下重试带类型的可重试失败，使用新的截止时间，并且要意识到先前的工作可能已经执行过。

对于远程处理器，出口策略是适配器选择的一部分。只有任务声明的帧字段和必需的关联元数据会离开主机；凭据、无关的点位、内部存储标识符和控制能力都不会。

## 7. 校验 ProcessingResult 和 DerivedData

传输成功并不意味着处理器输出可信。`DataProcessingApplication` 校验通用的 `ProcessingResult` 信封及其带任务类型的处理器输出。只有在此之后，Aether 才会为使用方签发 `DerivedData`。

通用检查包括：

- 受支持的结果契约版本；
- 匹配的请求 ID、任务 ID、绑定修订号和输入摘要；
- 所选处理器和制品的身份、版本和摘要；
- 有限的数值输出和预期的工程单位；
- 预期的输出形状、时间戳数量和严格有序的时间轴；
- 与任务相关的范围和一致性约束；
- 发布时间、处理器出处、质量和有界的过期时间；
- 显式的 `produced`、`fallback` 或 `unavailable` 状态。

对于预测，校验还要求时间戳落在所请求的未来范围之内，并且在存在置信区间或分位数时其顺序正确。

只有当任务允许某个具名的回退、并且结果标明了它时，处理器才可以返回回退数据。经批准的持续性预测可以在质量降级的情况下使用；异常之后产生的全零数组则不能报告为成功的预测。无效的输出会使整个结果被拒绝，而不是把部分可信的值泄漏给使用方。

## 8. 返回派生数据

版本 1 直接从带认证的 `POST /api/v1/data-processing/process` 路由返回经过校验的 `DerivedData`。它没有实现结果缓存、重放存储、持久的派生数据接收器、CLI 绑定或 MCP 工具。只有在它们的权威、保留和副作用策略得到定义之后，这些才可能成为独立的能力。

`DerivedData` 不会进入归 IO 所有的 T/S 槽，也不会伪装成测量点位。它的出处、质量摘要和过期时间对 HTTP 使用方保持可见。

## 9. 在不跨越子系统边界的前提下交接

下列交接方式保持了各自的所有权：

v1 只实现了带认证的 HTTP 响应。其余各行是对未来可能的使用方的约束，而不是当前的集成。

| 来自数据处理 | 使用方 | 允许的交接 | 不允许 |
|----------------------|----------|-----------------|-------------|
| 预测或估计 | 带认证的 HTTP 调用方 | 返回带类型的派生数据和出处 | 暴露任意的源数据或处理器密钥 |
| 检测评分 | 告警应用 | 提交一条带类型的观测，供告警策略评估 | 在处理器内部创建、确认或清除告警 |
| 预先计算的结果快照 | 未来的确定性规则或调度器 | 读取经过校验且未过期的数据，热路径中没有网络 I/O | 在规则执行期间同步调用远程处理器 |
| 预测或其他派生数据 | 未来的规划器/优化器 | 作为一项质量受限的规划输入使用 | 把结果当作设备命令 |
| 未来规划器提出的动作 | `ControlApplication` | 按正常流程重新授权、约束、确认、审计和下发 | 因为输入由处理器产生就绕过控制策略 |

因此，自动化控制使用另一套独立的顺序：

```
future scheduled planning cycle
        │
        ▼
DataProcessingApplication.process
        │ validated, unexpired DerivedData
        ▼
planner / optimizer / deterministic policy
        │ proposed actions
        ▼
safety constraints + permission + confirmation + audit
        │
        ▼
ControlApplication
        │
        ▼
existing SHM + UDS command path → aether-io → device
```

处理不可用时，规划周期要么使用显式配置的确定性回退，要么跳过该周期。它不会在设备重新连接时继续执行已过期的计划或重放过期的命令。采集、不依赖派生数据的规则、告警和安全行为继续运行。

AI 可以解释输入水位线、缺失情况、处理器/制品版本、回退和过期时间，因为这些事实都在结果契约中。它并不会因此获得一条从 `DerivedData` 通往 SHM 或设备的路径。

## 失败行为

在边缘，失败是意料之中的，并且有确定性的、可观察的结果。

| 失败 | 要求的行为 |
|---------|-------------------|
| 任务/绑定未知、被禁用或不兼容 | 在读取数据或调用处理器之前拒绝 |
| 历史不可用或水位线过旧 | 把帧标记为不可用；只使用任务声明的、不凭空编造观测的回退 |
| SHM 不可用、未写入或过期 | 不用 Redis、镜像或零值代替；只有当任务显式允许仅使用历史输入时才继续 |
| 必需的协变量缺失，或其发布时间晚于 `as_of` | 拒绝该帧，或者使用具名的协变量回退并降低质量 |
| 间隙过大、时钟偏差或单位/符号不匹配 | 在帧校验阶段拒绝；不要让处理器去猜 |
| 处理器超过截止时间、断开连接、过载或熔断器打开 | 返回处理器不可用；限制重试次数，并且不影响采集/控制 |
| 处理器契约或制品不匹配 | 拒绝完整的结果，并暴露这种不兼容 |
| NaN、无穷大、形状错误、时间戳错误或任务约束无效 | 把完整的结果作为无效的处理器输出拒绝 |
| 处理器使用了经批准的回退 | 保留其名称和降级后的质量，使使用方可以应用任务策略 |
| 规划无法获得可用的派生数据 | 跳过该周期，或者运行经批准的确定性回退；不下发过期的动作 |
| AI 客户端断开连接 | 确定性的边缘行为继续运行；数据处理不在硬实时回路中 |

每次失败都保留请求 ID 和机器可读的类别。可观测性数据可以记录来源水位线、缺失情况、耗时、处理器健康状况、制品身份和校验原因，同时避免记录原始的敏感帧载荷，除非有显式的保留策略允许。

## 边界总结

```
raw protocol bytes
        │
        ▼
IO decode and canonical T/S publication
        │
        ▼
SHM live authority ──► history persistence/query
        │                       │
        └──────────┬────────────┘
                   ▼
          Aether Data Processing
   bounded ProcessingFrame → DataProcessor
                   │
                   ▼
       validated, expiring DerivedData
          │          │           │
          ▼          ▼           ▼
       query UI   alarm policy  planner
                                 │
                                 ▼
                         ControlApplication
```

批量 ETL、数据仓库、仪表盘和任意的 BI 查询位于这条运行期边缘路径之外。确定性规则和告警生命周期仍是各自独立的应用。数据处理把受治理的观测与有界的派生结果连接起来；它不会吞并两侧的系统。
