# 规则引擎

Aether 的规则引擎位于 `aether-rules` 库中，运行在 automation 内部。它由三部分组成：解析器把可视化编辑器的流程文档转换为紧凑的执行拓扑，调度器决定每条规则何时运行，执行器遍历拓扑、评估条件并写入动作点位。本页介绍引擎的工作机制；如何把控制策略表达为规则流程（附一个完整的荷电状态示例），见[控制策略](https://github.com/EvanL1/AetherEdge/blob/main/docs/domain/control-strategies.md)。

## 两列，一个写入方

每条规则在 SQLite 的 `rules` 表中以两个并行的列持久化：

- `flow_json` — 完整的 Vue Flow 编辑器文档：带位置和标签的节点、边、视口、元数据。可视化编辑器加载它来恢复画布。
- `nodes_json` — 引擎实际运行的紧凑执行拓扑：一个 `RuleFlow`，包含 `start_node` ID 和一张从节点 ID 到执行节点的映射。解析器（`extract_rule_flow`）只保留执行所需的内容，丢弃位置、标签和边的样式。

不变量是：两列始终由同一个函数 `aether_rules::flow_column_values()` 一起产生，它解析编辑器文档并返回一个 `FlowColumns` 结构体，其中保存两个序列化后的字符串。该结构体使用具名字段而不是元组，这样调用处在绑定 SQL 参数时就不会悄悄把两个值弄反；无效的流程会整体失败，不存在部分输出。没有任何代码路径单独序列化其中某一列。

生产环境中有三个调用处，任何新增的 `rules` 表写入路径都必须经过同一个函数：

- `libs/aether-rules/src/repository.rs` 中的 `repository::upsert_rule`（用于规则导入）
- `services/automation/src/api/rule_routes.rs` 中的 `PUT /api/rules/{id}` 处理函数
- `tools/aether/src/core/syncer.rs` 中的配置同步器（`aether sync`）

一个细节：`POST /api/rules` 创建的是只有元数据的占位记录，即一个空的 `{}` 拓扑、一个 NULL 的编辑器文档和 `enabled = false`。流程内容总是稍后通过 PUT 到达，由 PUT 同时派生出两列。以仅紧凑形式导入的旧规则保留 NULL 的 `flow_json`；它们的 `nodes_json` 仍然来自同一个函数。

这一点为什么重要：如果两列出现分歧，编辑器显示的是一套逻辑，引擎执行的却是另一套，审查策略的操作员读到的就是假象。让每次写入都汇聚到同一个生产者，使这种分歧在结构上不可能发生，而不必依赖代码评审来把关。

## 调度

单个调度循环（`RuleScheduler::start`）用 `tokio::select!` 复用两个输入：一个周期性的定时节拍（默认 100 ms，`DEFAULT_TICK_MS`），以及在接入 PointWatch 事件平面时的一个有界的点位变化事件通道。规则在其 `trigger_config` 列中声明两种触发类型之一：

- **Interval**（`{"type": "interval", "interval_ms": 1000}`）— 只要某个节拍上距离上次执行的时间达到了 `interval_ms`，规则就到期。没有 `trigger_config` 的规则默认使用 1000 ms 的间隔（如果设置了 `cooldown_ms`，则以它作为周期）。
- **OnChange** — 规则通过 `point_refs` 订阅特定的测量点位（M）或动作点位（A），当订阅的值变化超出其死区时触发。

OnChange 规则由两条并行运行的路径提供服务。快速路径是事件驱动的：当订阅的点位被写入时，io 发布一个 PointWatch 事件。这个 16 字节的事件只携带带类型的地址和槽唤醒提示。automation 根据固定的清单校验它，重新读取该 SHM 世代，然后才让分发器把完整的 `(channel, kind, point)` 地址映射到规则 ID 并唤醒调度器，因此数值标识符相同的 T/S 点位绝不会唤醒对方的规则。节拍路径是回退手段：每个节拍，调度器在一个批次中采样所有订阅的点位，并重新评估每条 OnChange 规则；这覆盖了多点位规则，并在事件套接字不可用时让规则继续触发。

两种死区用于过滤噪声，以 AND 语义组合：

- `time_deadband_ms` — 规则级的频率限制；自上次触发起未经过这么长时间，规则不会再次触发。
- `value_deadband` — 绝对值（`|new - last| > threshold`）或百分比。不设置时，有限值之间的任何变化都算数。

NaN 值（Aether 的“暂时不可用”哨兵）从不算作变化；间隙之后的第一个有限值会触发一次。每次成功触发后，各点位的“上一个值”会前进到执行器在执行过程中实际读到的值，因此之后的比较以规则逻辑实际看到的值为基准。

到期的规则以有界的并行度并发执行（默认同时四条）。与触发器无关，规则还可以声明 `cooldown_ms`；冷却期只在一次成功且至少执行了一个动作的执行之后开始，并在其结束之前抑制再次执行。

调度执行和显式执行的规则都有 30 秒的截止时间。执行失败会保留 OnChange 基线和时间死区，在没有任何设备动作被接受的情况下允许同一个变化重试。超时可能使设备命令的结果处于未知状态；部分失败则可能已经应用了一些动作。这两种情况都会记录在规则历史中，并暂停对同一输入的自动重试。当订阅的点位出现新的有限值时，OnChange 规则重新具备触发资格。Interval 规则会一直保持暂停，直到其执行定义发生变化或一次显式执行成功。只修改元数据的编辑和无关的重载会保留这种暂停。在显式执行或编辑被暂停的规则之前，应先核对设备状态；截止时间无法撤销已被接受的命令。

## 执行

执行器从起始节点开始遍历紧凑拓扑，沿着每个节点的连线前进：`function-switch` 节点评估条件分支并选择一条输出连线，`action-changeValue` 节点向点位写入值，`action-calculation` 和 `action-periodDelta` 节点计算派生值，结束节点终止这条路径。这四个名称是线上格式，放在每个节点的 `data.type` 中；[编写规则](/zh/guides/writing-rules)给出了一份完整的文档。

Switch 在第一个匹配的分支处停止；缺少输出连线会使执行失败。ChangeValue 在发送该节点的动作之前检查每个赋值目标。相等比较会按操作数的量级容忍浮点舍入误差，并在零附近设有绝对的 epsilon 下限。

输入变量通过基于 SHM 的 `RuleLiveState` 读取，并且读取是严格的：如果某个变量的数据在本周期不可用，评估会短路，而不是代入默认值；缺失的读数绝不能像零值那样满足 `current < threshold` 之类的条件。同样的纪律也适用于写入：计算出的值如果是 NaN、无穷大或超出范围，就会被拒绝，该动作被记录为失败，绝不会被强行转换成某个数字。

对动作点位的写入走命令路径：执行器解析实例的模型到通道路由，然后通过 automation 的 HTTP 控制端点所使用的同一个 `ActionDispatch` 下发，即先写入共享内存的命令槽（C/A 槽），再通过 Unix 域套接字通知 io（见[共享内存](/zh/concepts/shared-memory)）。分发器在写入前后检查共享内存的写入器世代，因此跨越 io 重启触发的规则会被检测出来并丢弃，而不是落入过期的槽。

当目标不可用时，例如 io 重启后没有共享内存写入器、缺少 C/A 槽，或者通知套接字处于降级状态，动作会被记录为失败并附带原因，规则的成功标志也会反映这一点。命令从不排队等待稍后交付：下一个周期会根据当前值重新评估，而不是对一台恢复后状态已经不同的设备重放过期的设定值。

## 结果与可观测性

每次执行都会产生一条结果记录：成功标志、已执行动作的列表（每个动作带有目标、点位、值和各自的成功标志）、以已访问节点 ID 表示的执行路径、匹配的条件、变量值的快照，以及各节点的执行详情。调度器把这条记录写入本地持久且可观察的位置：

- 写入每条规则各自的日志文件，使每条规则都有一份独立、可用 grep 检索的历史；
- 写入 SQLite 的 `rule_history`，为 API/WebSocket 使用方保存结构化的执行结果和错误。

规则执行和结果观察都不需要外部数据库。

## 热重载

`POST /api/scheduler/reload` 调用 `RuleScheduler::reload_rules`，它从 SQLite 重新读取所有已启用的规则，并在写锁之下整体替换调度器内存中的规则集；正在运行的执行会按照它们开始时的规则完成。在接入了 PointWatch 句柄的情况下（生产模式），重载随后会根据新的规则集整体重建事件平面：包括告诉 io 要为哪些点位发布事件的订阅位图，以及把完整的 `(channel, kind, point)` 地址映射到规则 ID 的分发器索引。新增或改变了目标的 OnChange 规则会立即开始接收事件，无需重启服务。

实践中很少需要这个端点：规则的 CRUD 端点（创建、更新、删除、启用、禁用）各自都会在写入数据库后触发同样的重载。显式重载对带外写入才有意义，例如批量导入，或者 `aether sync` 从配置推送规则文件，否则调度器不会知道表已经发生变化。
