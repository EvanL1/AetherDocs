# 共享内存

Aether 中的实时值在热路径上不经过消息代理或数据库。io（通信服务）和 automation（模型/规则服务）共享一个归 IO 所有的点位段和一个独立的通道健康段，并通过 Unix 域套接字交换固定大小的通知。一份小型的提交见证证明这两个段来自同一次物理拓扑发布。设备读数在几十纳秒内就能落入共享内存。本页介绍共享内存段本身，以及构建在它之上的两个基于套接字的信令平面。它周围的服务见[系统架构](/zh/concepts/architecture)；这些值的含义见[数据模型](/zh/concepts/data-model)。

事实来源：`crates/aether-dataplane/`（物理标头、槽、锁）、`libs/aether-shm-bridge/`（带类型的清单、点位/健康发布和自愈读取器）以及 `services/io/src/core/channels/shm_listener.rs`（命令监听器）。

## 布局

实时状态段由一个 64 字节的标头和紧随其后、大小精确的 32 字节点位槽数组组成。`crates/aether-dataplane/src/core/header.rs` 中的 `calculate_file_size` 恰好等于 `64 + 32 × slot_count`；备用容量不会被映射到文件中。组合层仍会在创建之前执行配置的资源上限，但这个安全上限不属于物理 ABI。标头和槽的大小在编译期断言。通道健康使用第二个大小精确的段，每个配置的通道对应一个紧凑排列的槽。

文件路径由 `default_shm_path()`（`crates/aether-dataplane/src/core/config.rs`）按以下顺序解析：

1. `AETHER_SHM_PATH` 环境变量（如果已设置）。
2. `/shm/aether/aether-live-state.shm`，如果 `/shm/aether` 目录存在（Docker 部署在那里挂载一个共享的 tmpfs 卷）。
3. Linux 上为 `/dev/shm/aether-live-state.shm`（基于内存的 tmpfs）。
4. 其他情况下为 `/tmp/aether-live-state.shm`（macOS 开发环境）。

v5 标头（`ShmHeader`，`#[repr(C, align(64))]`）携带 `AETHER__` 魔数、布局版本、活动的 `slot_count`、所有者心跳、`layout_hash`、`writer_generation` 和 `publication_epoch`。其中没有物理的 `max_slots`、最后更新时间戳，也没有命名含糊的路由字段。所有多字节字段都使用本机字节序，因此读取器和写入器必须运行在同一种体系结构上。

每个 `PointSlot` 保存一个工程值（f64 位模式）、一个原始值（f64 位模式）、一个毫秒时间戳、一个 seqlock 序列计数器以及采集质量码。写入路径中没有脏标志，也没有配套的脏位图。从未写入过的槽在两个值字段中都保存静默 NaN 哨兵，也就是说未写入的槽是自描述的，绝不会与真实的设备零读数混淆。下游使用方会拒绝非有限值并解码存储的质量；未知的质量码会失败关闭。

槽通过扁平索引寻址。`ChannelPointManifest` 按确定性的通道/类型/点位顺序编译配置中确切的物理地址；稀疏的点位 ID 不会产生隐式地址或空洞。它唯一的填充规则是：当一个通道同时拥有 T/S 点位时，把该通道的第一个 C/A 槽对齐到 64 字节的缓存行边界，使两类写入权威不落在同一个缓存行上。`ChannelHealthManifest` 独立地把配置的通道 ID 编译成紧凑排列的健康槽。两者是否一致，通过各清单的 `layout_hash`、精确槽数量、已提交的发布纪元和写入器世代来验证。逻辑上的测量/动作路由和协议寄存器映射不参与任何一种物理布局。

拓扑的扩大和缩小绝不会原地调整已映射的活动 inode 的大小。io 构建一个大小精确的暂存世代，只为完全相同的 `(channel, kind, point)` 地址复制状态，然后原子地发布新的 inode。新增的点位以未写入的 NaN 哨兵开始；被移除的点位随之消失；未变化的点位即使槽索引改变，也保留值、原始值、时间戳和质量。读取器会隔离已退役的世代，并通过规范路径重新连接。

活动的 mmap ABI 并不是持久化快照格式。快照 v1 使用自己的 `AETHSNAP` 标头（`slot_count` 加 `layout_hash`），并为每个槽写入一条显式的“缺失/存在”记录；存在的记录包含值、原始值、时间戳和质量。它有意不包含心跳、写入器世代、发布纪元和 seqlock 状态。v5 之前的活动布局以及所有更早的快照表示都会被拒绝；没有针对旧版本的解码器。

## 写入所有权由类型强制

通道点位有四种槽类型：遥测（T）和信号（S）属于测量侧；控制（C）和调节（A）属于动作侧。所有权规则是：

- **io 采集拥有 T/S 槽**。`ShmAcquisitionStateWriter` 只接受带类型的 `AcquiredPointSample` 批次，并在任何修改之前拒绝 C/A 地址。
- **受治理的命令下发镜像 C/A 槽**。`ShmDeviceCommandSink` 解析出一个带类型的物理目标，在镜像前后检查写入器世代，并把完整的命令帧发送给 io。它不能写入 T/S 地址。

这种保护主要通过适配器端口边界上的类型实现；按原始槽索引的写入只留在物理适配器内部。运行时检查为清单成员关系、槽边界、世代稳定性和规范文件身份提供纵深防御。

普通的点位写入和通道健康写入不会更新存活状态。点位平面和健康平面的心跳由专门的 io 任务发布，因此 automation 的 C/A 镜像写入无法冒充采集健康。读取器把缺失或过期的所有者心跳视为不可用。

`ShmReadTopologyGeneration` 提供生产环境的读取视图。它把点位清单和健康清单绑定到同一份提交见证，并固定两个写入器世代；调试工具仍可以显式打开单个物理段。

## 一致性：seqlock

每个槽由各自的 seqlock 保护：写入器先把序列计数器增加为奇数，写入值、原始值、时间戳和质量，再把计数器增加回偶数。读取器先读序列，再读数据，然后再读一次序列；只有两次读到相同的偶数值时，这份快照才有效。内存序方面，读取侧使用成对的 Acquire 栅栏，写入侧使用 Release 栅栏加 Release 递增；`crates/aether-dataplane/src/core/slot.rs` 中的注释解释了为什么在 AArch64 上单次 Acquire 加载是不够的。

数据平面对每个槽只执行一次 `try_load_consistent()` 尝试。序列为奇数或发生变化时返回竞争，而不是在异步运行时线程上自旋；调用方在下一个有界的读取周期重试。生产数据平面中没有自旋重试循环。

`SlotSource::read_slots` 把一次多点位操作变成一个批量读取会话。`ReconnectingSlotSource` 为整个批次固定一个 mmap 读取器和一把本地读锁，检查一次心跳，并在批次前后校验写入器世代和发布身份。单个槽各自满足 seqlock 一致性，但整个批次并不是跨槽的原子快照。任何槽竞争或隔离失败都会使整个批次被拒绝。历史服务使用这个契约，而不必为每个选定的序列重复执行文件身份、时钟、标头和锁的相关工作。

## 世代与重建

三种身份让读取器能够发现自己的视图已经过期：

- **`layout_hash`** 是确切物理槽布局的指纹。io 在创建时写入它；每条协调的打开路径都会根据本地配置重新计算自己的指纹，不匹配时拒绝打开，否则槽索引会悄无声息地指向错误的点位。错误消息会提示操作员重启 io 以重新同步。
- **`writer_generation`** 标识写入器的一次运行实例。它在创建时由挂钟纳秒数与每进程随机数组合得到，并被强制为非零偶数：不变量是“静止时为偶数，重新配置进行中为奇数”，因此读取器遇到奇数值时会把自己挡在外面。命令/读取适配器在每次操作时都会比较世代，从而发现自己尚未跟上的 io 重启或重新配置。
- **`publication_epoch` 加提交见证**把点位文件和健康文件绑定到同一次已完成的 IO 事务。见证还记录了两者的哈希、数量和写入器世代。缺失、不完整、损坏或混杂的发布会以可重试的方式失败；读取器绝不会因为哈希相等而妄加猜测。

重新配置绝不会原地修改活动布局。`ShmWriterHandle` 和 `ShmChannelHealthWriterHandle` 构建完整的暂存文件，并在持有同一份跨平面发布租约的情况下，把它们原子地重命名覆盖到各自的规范路径。提交见证最后重命名，它就是线性化点。仍被保留的 mmap 通过奇数的写入器世代被隔离；自愈读取器只能重新打开其服务级拓扑所固定的纪元和写入器世代。历史服务和上行服务把它们的 SQLite 路由和已提交的 SHM 读取视图作为同一个 `Arc` 整体替换，因此一次采集过程不会混用逻辑世代和物理世代。崩溃遗留的暂存文件数量有界，并在恢复时被清理。

物理契约只有 v5。旧的 v4 mmap、旧的快照，或者 v4/v5 混合的进程集合都是无效输入。升级方式是停止六个服务，删除过时的运行时文件，然后启动完整的 v5 组合，让 io 发布新的点位/健康对和提交见证。

## 命令通知

当 automation 发出命令时，无论是规则动作还是 HTTP 控制请求（哪些内容允许到达设备，见[应用与智能体的安全操作](/zh/guides/safe-operations)），`ShmDeviceCommandSink` 都会把 C/A 值镜像到被固定的写入器世代，并通过 Unix 域套接字（`/tmp/aether-m2c.sock`）发送通知，使 io 立即响应而不必轮询。实测中通知路径为亚毫秒级；约 1–2 ms 是下发代码为正常路径记录的设计预算。

通知（`DeviceCommandFrame`）是一个固定 56 字节的帧，携带路由目标（通道、点位类型、点位）、命令载荷（值的位模式加上发出时间戳和过期时间戳）以及生产者顺序信息（`producer_id`，即每次运行实例各不相同、每次 automation 重启都会改变的 ID，外加单调的 `seq`）。由于帧中携带了完整的命令，io 永远不必回读槽，而对同一点位的两次快速写入会作为两个事件到达，不会合并成一个。

io 的 `ShmCommandListener` 绑定该套接字，并立即把它的权限限制为 0600（如果限制失败则拒绝监听，因为任何能写入这个套接字的人都能注入设备命令），然后按点位对传入事件去重：不同的 `producer_id` 总是会重置状态（automation 发生了重启），而在同一个生产者之内，则使用回绕序列比较（`seq.wrapping_sub(last_seq) > u64::MAX / 2`）把过期或重复的帧丢弃。已过期的帧在入队之前就被丢弃。随后，统一的通道任务会在调用协议适配器之前，立即根据配置的可写点位、包含端点的最小值/最大值和步长再次检查该值。未知点位、无效的点位约束、NaN/无穷大以及批次中任何被拒绝的成员，都会使整条命令失败，并且不触碰硬件。在发送侧，`ShmNotifier` 对失败的写入重试三次，然后把自己标记为断开，并以指数退避重连（从 1 秒开始翻倍，上限 5 秒）。没有轮询回退：如果套接字一直不可用，通知结果会报告交付降级，由调用方决定向上呈现什么。

## PointWatch 事件平面

命令的流向是 automation → io；PointWatch 是相反的方向，规则引擎正是靠它实现事件驱动（见[规则引擎](/zh/concepts/rule-engine)）。每次写入 T/S 槽之后，io 都会查询每个使用方的**订阅位图**，这是位于主段旁边、由原子 u64 字组成的独立带版本 mmap。它的容量来自部署的 `shared_memory.max_slots` 资源上限；其精确长度为一个 32 字节的自描述标头加上 `ceil(max_slots / 64) × 8` 字节。因此它没有编译期固定的 100,000 槽上限。路径由解析出的实时状态路径派生，例如 `aether-live-state-point-watch-subs-automation.shm`；automation、alarm 和 API 各自拥有独立的位图和套接字。常见的未被订阅路径上，每个使用方只需一次宽松的原子加载和一次位测试。

位图的创建通过一个原子发布的权威附属文件串行化。该附属文件对非所有者是只读的，因为建议性锁从不需要修改它的内容；新发布的位图权限为 `0666`，这样以 root 身份运行的 io 进程和显式降权的使用方可以映射同一批原子字。重新打开一个有效的位图绝不会改变它的属主或权限。标头把魔数、格式版本、容量和字数绑定到精确的文件长度。过时、格式错误或容量不匹配的文件绝不会被解码；组合所有者会改为发布一个干净的位图世代。

命中时，io 构建一个 16 字节的小端序 `PointWatchEvent`：`channel_id`（u32）、`point_id`（u32）、`slot_index`（u32）、点位类型（u8）以及一个三字节的 v1 帧标记。构造时会拒绝无法放入 u32 线上字段的槽，绝不截断。解码时会拒绝无版本或格式错误的帧，因此旧的发送方不会被误解。帧中不包含值、原始值、时间戳、质量、生产者 ID 或序列号。它只是一个唤醒提示，不能与 SHM 的权威性相竞争。一个后台任务以每批最多 64 帧的方式，把有界的进程内通道中的内容排空到每个使用方隔离的套接字上。

在 automation 一侧，整条管线从头到尾保持有界：监听器把帧转发到容量为 1024 的通道，分发器（`libs/aether-rules/` 中的 `PointWatchDispatcher`）完成 `(channel, kind, point) → rule IDs` 的映射，并把唤醒事件转发到调度器自己的容量为 1024 的通道。在分发之前，automation 会根据自己固定的清单校验带类型的地址/槽，并从同一个 SHM 世代重新读取样本。API 和 alarm 执行同样的清单校验和权威的 SHM 重读。每个阶段都使用非阻塞的 `try_send`；溢出时丢弃提示并递增 `dropped_count`，而绝不阻塞 io 的写入路径。周期性轮询仍是被丢弃提示的修复路径。

## 无需 HTTP 的本地可观测性

`aether-shm-bridge` 中的 `ShmObserver` 通过只读路径打开点位平面、通道健康平面和拓扑提交。它校验精确的 mmap 布局、稳定的世代、共同的发布纪元、提交身份以及专用心跳的时长。它可选的 O(N) 扫描会报告存在、未写入、质量、在线/离线、无效以及发生竞争的槽数量。它不会取得写入器权限、刷新心跳、修复文件或触发拓扑发布。

操作员使用现有的本地 CLI 入口：

```bash
aether shm info             # one human-readable observation
aether --json shm info      # script/agent observation
aether shm info --no-scan   # O(1) header and commit validation
aether shm top              # continuously refreshed terminal UI
aether shm serve            # optional loopback browser UI
```

`aether doctor` 使用同一个观察器，因此系统诊断和 SHM 仪表盘不会因为检查了不同的平面而得出不一致的结论。HTTP 是可选的，也不需要常驻的观察器进程。`aether shm serve` 内嵌一个自包含的页面和同源的 JSON 端点，只绑定到环回地址，并且只在 CLI 进程的生命周期内存在。它没有写入路由，也不能成为 SHM 的权威。
