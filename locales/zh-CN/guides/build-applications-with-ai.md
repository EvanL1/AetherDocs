# 使用 AI 构建应用

AetherEdge 在设计上就是无头的。它提供确定性的边缘运行时，以及 AI 智能体构建站点专用应用所需的机器可读契约。生成的网页界面、移动应用、CLI 或后端都是可替换的客户端：它绝不属于实时状态、期望状态或安全权威的一部分。

这是 AetherIoT 更宏大的 AI 原生方向中一块已经可用的基础：人描述想要的结果，智能体发现物理空间并生成受治理的变更，契约让这些变更可以被检查，AetherEdge 则在没有模型的情况下执行已投运的行为。完整的最终用户对话、仿真和持续适应生命周期尚未作为产品交付。见 [AI 原生平台](/zh/overview/ai-native-platform)。

本指南定义参考应用和下游产品共用的开发方法。

## 可选的智能体技能

可以选择把仓库中的 `aether-iot` 技能添加到兼容的编码助手。Bun 只用来运行第三方 `skills` CLI；这条命令不会安装 AetherEdge 运行时或 Rust SDK：

```bash
bunx skills add EvanL1/AetherEdge --skill aether-iot
```

这个技能有意保持精简。它教授工作流程，并把智能体引导到当前的在线文档，而不是内嵌一份过时的副本。文档服务发布：

- `/llms.txt`：精选的文档索引；
- 每个页面的 Markdown 副本，在地址后追加 `.md` 或发送 `Accept: text/markdown` 即可获取。

智能体应先读取这份精简索引，只获取当前任务需要的页面，而不是加载整个文档语料。

当智能体还需要实时的运行时信息时，再连接 `aether mcp`。默认的 MCP 接口面是只读的；不要仅仅为了生成应用就启用写入。

## 使用契约栈

应用应当按以下顺序发现 AetherEdge：

| 来源 | 它确立的内容 |
|---|---|
| 运行时清单 | 确切的内核版本、目标、特性、协议和能力 |
| 当前激活的 Pack | 领域词汇、支持的资产和兼容性要求 |
| OpenAPI | 确切的 HTTP 路径、结构定义、状态码、认证和命令策略 |
| MCP | AI 客户端可用的实时工具和结构化运行时结果 |
| 在线 Markdown | 架构、工作流程、安全指引和领域说明 |

不要用 README 示例或模型记忆代替运行中发行版的 OpenAPI 文档。在版本化契约明确声明之前，不要假定某个已安装的 Pack、可选适配器或写入能力存在。

## 从只读用户故事开始

把第一条提示写成一个有边界的结果，例如：

```text
为这个 AetherEdge 站点构建一个只读运维页面。显示服务健康状态、
当前拓扑修订、带质量和新鲜度的点位值、活动告警，
以及最近一小时的可用历史数据。不要添加设备控制。
```

生成代码之前，智能体应先给出一份简短的能力清单：

1. 运行时和 Pack 版本；
2. 页面所需的查询和订阅；
3. 能够满足这些需求的公开能力；
4. 缺失或仍属内部的能力；
5. 用于生成客户端的确切 OpenAPI 文档。

缺失的公开查询是应用边界上的缺口。它不构成暴露内部服务端口、抓取 SQLite、挂接 SHM 或虚构端点的许可。

同样的规则适用于对话式配置。如果运行时没有声明某项能力，智能体必须报告这个缺口。它不能编造设备功能、悄悄近似某项策略，或者把自然语言中的自信转化为物理权威。

## 保持单一远程边界

只有 `aether-api` 用于承载远程应用流量。它在 `/api/v1/io`、`/api/v1/automation`、`/api/v1/history`、`/api/v1/uplink` 和 `/api/v1/alarm` 下发布固定的带认证命名空间；这些命名空间所属的进程 API 仍然留在环回地址上。

因此，生成的远程客户端必须：

- 只通过 6005 端口上带认证的 `aether-api` 调用这些带网关前缀的能力；
- 使用运行中网关的 OpenAPI 契约生成类型和请求；
- 在可用时使用它带认证的 WebSocket 契约获取实时更新；
- 报告某个用例不可用，而不是代理内部端口；
- 不让凭据进入源码管理、URL、日志，以及并非为保存机密而设计的浏览器持久化存储。

本地开发工具可以在边缘主机上查看环回地址上的 OpenAPI 文档，但这并不会把那些端口变成受支持的远程接口。

## 保留 IoT 状态语义

一个有用的 IoT 界面需要的不只是一个数值。请保留并显示以下契约字段：

- 点位身份和工程单位；
- 值以及健康状态或质量；
- 源时间戳和观测到的新鲜度；
- 物理拓扑纪元；
- 期望配置修订；
- 活动、降级或等待对账的运行时状态。

绝不要把缺失、陈旧、不健康或代次不匹配的数据静默强制转换为零。绝不要把期望状态和活动的运行时状态合并成一个乐观的状态。拓扑变更正在进行时，保持最后一个一致的代次可见，或者显示当前没有一致的视图。

展示名称、分组、单位、枚举和推荐的可视化方式属于当前激活的领域包 或下游应用。通用客户端不得从 AetherEdge 内核推断能源语义。

## 把命令作为单独的阶段添加

只有在只读工作流完成之后才引入命令。对于每条命令，都要呈现并执行服务端声明的契约：

- 风险和所需权限；
- 显式确认策略；
- 幂等性和预期修订行为；
- 请求关联和审计结果；
- 已接受、降级和不确定的结果。

保留返回的 `request_id`、`command_id` 和结果修订。在超时、审计不完整、已接受但降级的响应或物理结果未知之后，不要自动重试非幂等命令。设备命令被接受，只证明本地命令平面接受了请求；要表明物理执行，需要反馈遥测。

这些规则由后端强制执行。确认对话框是有用的呈现方式，但它绝不是安全边界。

## 验证生成的应用

每个持续维护的参考应用或下游应用都应通过：

1. 类型检查、代码检查、单元测试和生产构建；
2. 覆盖健康、陈旧、未授权、降级和不确定结果的契约测试夹具；
3. 一项检查，确认没有请求以直连进程端口、SHM 或 SQLite 为目标；
4. 只读默认配置，其中不存在控制组件和写入凭据；
5. 针对安全空或仿真 AetherEdge 组合的集成检查。

参考应用用于演示契约，并且可以被替换。它们不定义 API 行为、配置权威或领域事实。
