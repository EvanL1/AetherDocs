# AetherContracts 兼容性与发布门槛

> 本页是面向中文用户的说明。带标签版本中的英文规范、机器可读兼容性文件、测试夹具和 TCK 才是规范性依据。

兼容性以证据为依据。仅仅共享一个版本字符串，或成功解码一个测试夹具，都不能证明完整互操作性。最新发布版本是 `v0.1.0-alpha.4`。仓库的 `0.1.0-alpha.5` 开发目标尚未发布。两者都处于实验阶段，旧传输继续作为默认值。

## 当前产品基线

| 产品        | 契约关系                                                                                   | 当前状态                                     |
| ----------- | ------------------------------------------------------------------------------------------ | -------------------------------------------- |
| AetherEdge  | 提交 `947f9303810fa116afa9c4c301c5e388a181b332` 包含针对 `v0.1.0-alpha.3` 的完整使用方锁   | 仅有分发证据；alpha.4 采用与产品门槛仍未关闭 |
| AetherCloud | 提交 `8a14f7464bf67ce16b4e8cd473e0689cea7f1b13` 包含针对 `v0.1.0-alpha.3` 的完整使用方锁   | 仅有分发证据；alpha.4 采用与产品门槛仍未关闭 |
| 独立实现    | 精确发布包、封闭使用方锁、公开测试夹具与 TCK                                               | 受支持的分发路径；一致性必须由使用方自行证明 |

该矩阵固定了包含这两份锁的公开产品提交，两份锁指向同一个已发布的 alpha.3 制品全集。它们不能证明 alpha.4 已被采用，也不能证明生产身份、完整状态机行为、崩溃持久性或安全的旧传输切换。机器可读的产品证据是 [`compatibility/product-matrix.json`](https://github.com/EvanL1/AetherContracts/blob/main/compatibility/product-matrix.json)。

## 语言绑定兼容性

| 绑定             | alpha.4 中已实现的范围                               | 尚未声明                            |
| ---------------- | ---------------------------------------------------- | ----------------------------------- |
| TypeScript       | 规范 `uint64`、JSON 规范化、公开夹具清单             | 完整的生产结构定义与传输编解码器    |
| Rust             | 全范围规范 `u64`、类型化失败、公开夹具清单           | 完整的生产 JSON、模型与传输编解码器 |
| C99              | 有界规范 `uint64`、无分配 P/M/A 查询、有界夹具配置档 | 完整的生产 JSON、模型与传输编解码器 |
| C++17            | C99 核心上的轻量视图与结果                           | 独立线协议语义或第二套编解码器      |
| Go、Java、Python | 规划中                                               | 当前没有已发布的一致性绑定          |

稳定的字符串失败代码属于契约。数值错误值和消息文本仍由具体语言绑定决定。映射错误或重试行为前，请先阅读机器可读的 [`compatibility/failure-codes.json`](https://github.com/EvanL1/AetherContracts/blob/main/compatibility/failure-codes.json)。

## 兼容性规则

- 协议 `uint64` 值使用规范十进制字符串。
- Integration 观测中的 `int64`、十进制和字节值使用各自配置档规定的有界规范字符串。
- Integration 显示文字与证据文字不能为空白，并且不包含 C0 控制字符或 DEL。
- 核心 JSON 对象是封闭对象，未知字段会被拒绝。
- 重复键、无效 Unicode、不安全数字和无界输入都会失败关闭。
- 会话质询请求使用既有的 `up/session` 路由，不是认证证据；只有其网关凭据绑定处于有效投运状态且请求通过限速时，才可能触发质询签发。
- 对未到期质询的重试会重新发布完全相同的已持久化质询；质询消费与会话接纳以原子方式提交，且恰好一次。
- 质询有效期采用严格比较：`evaluation_time_ms < expires_at_ms`，因此二者相等即已到期。
- 网关签名的交付与心跳分别使用各自精确的 `aether.cloudlink.uplink-signing.v1alpha1` 投影。交付中缺失的到期时间，以及仅在心跳中缺失的全部六个交付值，都映射为 JSON null。
- 带签名的心跳在新鲜度或重放评估之前，先绑定有效密钥、已接纳会话、凭据代次和协商得到的心跳间隔。其明确的未来边界与陈旧边界使用带溢出检查的 uint64 运算，精确重放绝不刷新服务端存活状态。
- 网关签名的交付重放会持久保存四字段位置身份、一个与会话无关的不可变摘要，以及一个当前会话绑定。同一会话内的精确重放，或严格更高的当前会话代次，可以恢复当前会话回执而不重复业务效果。同代次的会话变化、会话代次回退、凭据代次变化以及不可变交付内容的变化都会导致认证失败。
- 只有与其业务效果原子提交的重放记录才可以绕过原始到期时间；待定的认证记录不可以。首次效果仍受到期时间约束，而已经提交的精确交付可以在到期后更新其当前会话绑定；该绑定先持久化，回执才会重新签发。
- 每个 MQTT 前缀都是一个授权命名空间。网关标识在其中唯一；多租户部署隔离租户或项目前缀，或者使用云端全局唯一的网关标识；每个消息代理主体的权限限定在一个精确的命名空间和网关主题集合内。前缀和主题仍不足以作为认证证据。持久交付查询先选择这一可信命名空间分区，再使用保持不变的四字段线协议重放身份；禁止不分区的全局查询，也禁止跨命名空间复用记录。
- alpha.4 的 `session-accepted` 没有签名，也不与其质询和客户端请求关联。带签名、可抵御跨握手重放的会话接纳是下一版本的生产门槛，而不是 alpha.4 隐含的保证。
- Integration Control 回执中的 `failure_code` 值最长为 128 个字符。
- MQTT 确认只是传输证据，绝不是应用层持久接纳。
- Thing Model 能力是声明，不是授权。
- CloudLink 不包含直接物理控制操作。
- 后续编码需要显式协商和自己的 TCK。
- alpha.3 CloudLink 使用方会拒绝 alpha.4 Integration 消息类型；混合版本部署保持扩展关闭，而不是通过发送数据探测支持情况。

未来每个发布版本都应公布精确产品版本或提交，并链接到可执行证据。浮动的 `main`、`latest` 和隐含兼容性都不是发布证据。
