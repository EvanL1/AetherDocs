# AetherContracts 基础规范

> 本页帮助中文用户理解协议。带标签版本中的英文规范、JSON Schema、测试夹具和 TCK 才是规范性依据。

v1 alpha 的逻辑表示和线编码均为 UTF-8 JSON。封闭的核心对象拒绝未知字段。符合要求的原始解码器还必须拒绝重复对象键、格式错误的 Unicode、超过配置档限制的输入，以及脱离契约声明的语义就无法表示的 JSON 数字。

协议 `uint64` 值是规范十进制字符串。它们不带正负号、空白、小数点、指数或前导零，只有零恰好写作 `"0"`。`uint64` 的最大值是 `"18446744073709551615"`。Thing Model 可以声明 `int64` 值类型。Integration v1 alpha 1 配置档把其观测到的有符号表示冻结为范围 `[-9223372036854775808, 9223372036854775807]` 内的规范十进制字符串：不接受正号、空白、小数点、指数、前导零或负零。其他模块不会仅因声明该类型就获得有符号线协议语义。

Integration 观测的十进制数和字节同样使用契约声明的字符串，而不是有损的 JSON 数字转换或实现原生的字节强制转换。它们的规范语法、边界和 Base64url 尾随位规则由 Integration 结构定义、规范、测试夹具和 TCK 冻结。

Integration 的显示文字和证据文字的长度由声明它的结构定义限定。它必须至少包含一个非空白字符，并且不得包含 C0 控制字符（`U+0000` 至 `U+001F`）或 DEL（`U+007F`）。使用方不得把这些字段当作原始终端文字、提供方载荷或机密载体接受。违反时以 `TEXT_INVALID` 失败。

验证顺序属于契约：检查语言绑定输入类型之后，长度超过 20 字节的表示先以 `INTEGER_OUT_OF_RANGE` 失败，然后才检查数字语法。这让无分配的 C 解码器保持有界，也让每种语言对超长对抗输入给出相同的失败。

通过 JSON Schema 是必要条件，但并不充分。排序、重放、身份冲突、授权、修订兼容性与持久回执语义需要上下文验证器和 TCK 场景。

JSON 数字使用有限 IEEE 754 binary64 语义。如果解码后的值是整数值，但超出可互操作安全整数范围 `[-9007199254740991, 9007199254740991]`，只有当其 RFC 8785 序列化保留小数点时才被接受；否则生产方必须使用契约声明的十进制字符串。因此，`1e100` 与 `1.5e20` 以 `JSON_UNSAFE_NUMBER` 失败，而 `1e-100` 和 binary64 最大值 `1.7976931348623157e308` 仍是浮点值。协议整数绝不使用这项例外：它们使用各自明确冻结的字符串编码。

TCK 严格解码器为嵌套层级、字符串、集合和数字标记应用防御性的参考运行器预算。这些默认值是实现安全限制，不是可移植的接纳上限。传输或制品配置档在互操作需要时冻结可移植限制；MQTT 配置档目前把完整消息冻结为 262144 字节。其他语言绑定可以应用有记录的更严格资源限制，并且必须以 `FIELD_BOUND` 失败关闭。

契约定义签名对象时，必须在使用前规定精确的签名投影。它使用 RFC 8785 JSON Canonicalization 序列化，使用 SHA-256 计算哈希，然后签名。经过美化排版的源字节绝不是签名输入。本 alpha 版本不在全局范围冻结 CloudLink 认证投影：经显式选择的实验性配置档在
`profiles/cloudlink/v1alpha1/authentication.json` 中冻结其两个 Ed25519 签名投影，而生产密钥生命周期和验证方归属仍未解决。签名确认的投影仍在规划中。

稳定的字符串失败代码与语言无关。在未来的 ABI 配置档明确冻结之前，数值和错误文字属于语言绑定细节。
