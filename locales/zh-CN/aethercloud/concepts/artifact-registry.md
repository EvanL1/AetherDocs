# 制品注册表与不可变发布

> 权威来源：[AetherCloud](https://github.com/EvanL1/AetherCloud/blob/main/docs/concepts/artifact-registry.md)。此页面镜像到统一的 AetherIoT 文档中。

AetherCloud 把 Pack、配置、模型、规则和应用修订版发布为不可变、按内容寻址的事实。发布使修订版有资格被之后的期望状态引用；它不会在 AetherEdge 运行时上部署、下载或应用任何内容。

## 权威与边界

- AetherCloud 是制品元数据、校验与发布状态、签名者策略和发布渠道引用的权威。
- 内容存储是由 SHA-256 摘要标识的不可变字节的权威。
- AetherEdge 仍然是本地兼容性检查、缓存状态以及修订版是否被接受和应用的权威。
- 发布渠道是受治理的引用。它不是可变内容，也不是部署的证据。
- 签名验证和发布审计是业务要求；采样的 OpenTelemetry 信号不能替代其中任何一项。

## 已实现的内层切片

领域包定义了有界 ID、规范 uint64 十进制的修订版值和内容长度值、SHA-256 摘要、兼容性要求、签名元数据，以及下面这个不可变状态机：

```text
draft -> validated -> published -> deprecated -> withdrawn
                            \---------------------> withdrawn
```

每次转换都返回一个冻结的新修订版，并保留身份、内容摘要、兼容性、依赖、签名和发布时间戳。发布不能跳过校验。撤回会保留此前的发布证据，而不是删除历史。

应用包实现了 `artifact.revision.publish` 和 `artifact.revision.get`。发布是高风险、需要明确确认、带有效期、幂等且经过审计的租户和项目命令。它精确解码外部输入，通过由应用拥有的端口验证内容和签名，之后才请求存储库以原子方式持久化已发布修订版、渠道引用、幂等性证据、审计证据和发件箱证据。

内存适配器是一致性实现。它证明：

- 精确重试返回原始修订版，不产生重复的审计或发件箱证据；
- 以变更后的发布身份复用幂等键会产生冲突；
- 修订版身份不能被替换；
- 发布渠道竞争不能悄悄替换其当前修订版；
- 内容长度与摘要检查以及可信签名检查以失败关闭方式处理；
- 持久化失败不会写入任何修订版、渠道、审计或发件箱证据；
- 租户和项目范围内的查找不会泄露其他租户的修订版。

## 存储契约

生产设计分离三项职责：

| 存储       | 职责                                                                             |
| ---------- | -------------------------------------------------------------------------------- |
| PostgreSQL | 制品与修订版元数据、发布状态、渠道引用、幂等性记录、授权范围、审计和事务性发件箱 |
| 对象存储   | 按摘要存放的不可变内容、签名材料、来源证明、SBOM 和大体量校验证据                |
| 边缘缓存   | 在 AetherEdge 策略下经本地验证的内容和应用证据                                   |

当前实现没有 PostgreSQL 或对象存储适配器。内存适配器的 `putContent` 和可信签名辅助函数是测试夹具，不是上传、KMS、CA 或生产签名者 API。

## 失败与重放语义

内容缺失、摘要或长度不匹配、签名无效、验证器或存储不可用、修订版冲突、发布渠道冲突和幂等性冲突都是类型化失败。任何失败都不会被转换成成功的发布。未来生产路由上的 HTTP 超时可以通过重放同一个幂等键来解决；客户端必须查询，而不是自行臆造发布结果。

发布事件目前只存在于原子内存适配器中。只有在持久事务写入真实的发件箱之后，`artifact.revision-published.v1` 才会成为生产集成事件。
