# 多云融合

> 权威来源：[AetherCloud](https://github.com/EvanL1/AetherCloud/blob/main/docs/concepts/multi-cloud-fusion.md)。此页面镜像到统一的 AetherIoT 文档中。

多云融合是 AetherCloud 的首要云端能力。它为租户提供横跨公有云、私有云、主权环境和本地基础设施的统一资源图、策略模型、计划工作流和审计轨迹。它不会假装这些提供商暴露的资源完全相同。

## 公共层

AetherCloud 拥有一套精简的、由能力驱动的词汇：

- 提供商和云连接身份
- 区域、可用区和放置约束
- 各种能力，例如计算、对象存储、私有网络、托管 Kubernetes、托管 PostgreSQL 和物联网接入
- 部署堆栈、期望拓扑、已保存的计划、策略决定、作业和规范化的资源观测
- 成本、配额、健康状况、来源和新鲜度元数据

提供商公布自己可用的能力。放置只选择满足所请求能力和租户策略的提供商连接。选择是显式的；绝不会根据凭据的形态推断提供商。

## 当前实现

仓库目前实现了提供商描述符、CloudConnection、ProviderRegion 观测、动态 ProviderAdapter 注册表，以及经过授权的、租户/项目范围的 `DiscoverProviderRegions` 应用查询。输入和适配器输出要先经过运行时验证，才能成为规范化观测。可复用的一致性套件和内存适配器让这份契约不需要云账户就能执行。

领域层还实现了 DeploymentStack 定义，它的租户、项目、提供商、连接和状态键都从一个活跃的 CloudConnection 推导而来。状态后端是一个不透明的远程引用；加锁和加密是强制的，而不是由调用方选择的选项。放置观测必须匹配同一个提供商和连接，其区域才能被选用；堆栈会记录规范的观测时间，以便后续策略拒绝过期的放置证据。

应用层现已实现受治理的、租户/项目范围的 `PlanDeploymentStack` 命令、动态的 OpenTofu/Terraform `InfrastructureEngine` 注册表、运行时引擎输出验证、变更汇总、策略回执和幂等的计划存储库端口。共享的一致性套件、内存引擎和内存计划存储库让这份契约不需要云账户就能执行。真实的 OpenTofu CLI 适配器会动态探测自身版本、验证不可变的源制品、在有界的临时工作区中以纯 argv 方式运行并保存计划、解析版本化 JSON、通过加密制品端口存储计划，并证明注入的状态锁租约已被释放。该端口没有 Apply 操作。

真实的提供商 SDK 适配器、凭据解析、连接与 DeploymentStack 持久化、资源盘点 API、放置策略、生产远程状态与分布式锁、加密对象存储、沙箱化的工作进程部署、Terraform CLI 适配器以及 Apply 仍在规划中。发现和计划目前都还没有 HTTP 路由。做发现相关工作请遵循[添加提供商适配器](/zh/aethercloud/guides/add-provider-adapter)，做引擎相关工作请遵循[安全地规划基础设施](/zh/aethercloud/guides/plan-infrastructure)，不要另行发明新的边界。

## 提供商专属层

每个提供商适配器负责：

- 身份验证和短期凭据
- 区域、可用区、配额、SKU 和价格发现
- 提供商专属的基础设施模块
- 提供商原生的能力扩展
- 把引擎 JSON 和提供商 API 转换为规范化观测
- 针对提供商专属发现与规范化的一致性测试夹具

带命名空间的扩展保留那些不属于公共模型的能力。可移植性意味着意图和策略可以比较；并不意味着把每一项提供商特性都藏在一个虚假的通用 API 后面。

## 基础设施执行

OpenTofu 是默认引擎。Terraform 通过同一个 `InfrastructureEngine` 端口得到支持。已实现的应用流程选择一个不可变的版本化提供商模块和拓扑，请引擎生成一份已保存的计划，验证从版本化 JSON 得出的变更和状态锁证据，然后评估策略并记录加密制品引用。真实的本地 OpenTofu CLI 工作进程已经实现；它的生产远程状态、凭据、制品存储和工作进程部署适配器，以及所有 Apply 路径都在规划中。

```text
DesiredTopology
      ↓
PlacementPolicy
      ↓
Provider Adapter + versioned module
      ↓
OpenTofu/Terraform plan -out
      ↓
show -json → validation, summary, policy
      ↓
encrypted saved Plan receipt

future separate workflow:
approved exact Plan → Apply → refresh → NormalizedResourceProjection
```

基础设施引擎计算依赖关系和拟议的漂移。AetherCloud 拥有工作流、权限、策略、审计和规范化资源图。经策略批准的计划不是批准证据，也无法通过当前端口应用。直接使用的提供商 SDK 对引擎起补充作用，用于发现、定价、配额、临时凭据，以及不属于基础设施生命周期变更的操作。

## 状态隔离

一个状态属于一个部署堆栈。一个堆栈恰好属于一个租户、一个提供商连接、一个账户或订阅，以及一个主区域。在提供商支持的情况下可以存在跨区域模块，但一个状态绝不跨越多个提供商连接，也绝不是租户全局的。

状态使用具备加锁、加密、版本控制、备份和保留能力的远程后端。已实现的计划契约要求状态键精确关联，并要求锁已获取且已释放的证据。持久的状态谱系、序列号、提供商版本、备份和保留仍在规划中。工作进程保持无状态，绝不把本地工作区当作持久存储。

## 凭据

云连接包含元数据和机密引用，不包含明文凭据。工作进程优先使用工作负载身份或短期凭据，只为当次作业接收它们，通过提供商支持的环境变量或凭据机制注入，并在事后销毁工作区。凭据不得出现在生成的模块、已保存的计划、日志、提示词或规范化资源记录中。

## 多云运维

融合发生在各个状态文件之上：

- 跨提供商的资源盘点与搜索
- 综合成本、区域、主权、能力和配额的策略与放置
- 使用多个可独立审计的作业完成协调发布
- 跨边缘站点和云端目的地的数据路由意图
- 规范化的健康与漂移视图，并可查看提供商原生细节

跨云发布是由多个提供商范围作业组成的 saga，而不是分布式事务。部分成功保持可见，补偿是显式的。

## 控制平面数据库的可移植性

`managed-postgresql` 是一项可移植的提供商能力，而不是某个固定的厂商产品。未来的提供商配置档会保留原生引擎变体、支持的版本和扩展、HA、备份、加密、私有连接、复制、区域、主权、RPO/RTO、价格证据和带命名空间的扩展。核心持久化代码始终是一个 PostgreSQL 适配器，绝不按提供商枚举做分支。

每个 AetherCloud 控制平面单元有一个权威的 PostgreSQL 写入拓扑。跨多个提供商管理资源并不需要同步的跨云数据库写入。租户归属单元的放置、副本提升、灾难恢复和迁移都是显式的受治理工作流。用户可见的放置与隔离模型见 [PostgreSQL 持久化与多云单元](/zh/aethercloud/concepts/persistence-and-multi-cloud-cells)。

## 从 HPC-NOW 保留的经验

HPC-NOW 表明，可以在各自独立的提供商 IaC 模板之上建立一个有用的公共生命周期，也可以把提供商状态规范化为统一的多集群视图。AetherCloud 保留了这些思路，同时用注册表取代硬编码的厂商分支，要求显式的提供商身份，解析版本化 JSON 而不是原始状态文本，并把机密与模块分离。
