# 应用契约目录

> 权威来源：[AetherCloud](https://github.com/EvanL1/AetherCloud/blob/main/docs/reference/application-contracts.md)。此页面镜像到统一的 AetherIoT 文档中。

[`ai/application-contracts.json`](https://github.com/EvanL1/AetherCloud/blob/main/ai/application-contracts.json) 是应用能力、权限、命令治理、带类型的错误、集成事件、HTTP 操作和实现状态的机器可读索引。

`mcp_exposures` 单独报告资源／工具适配器是否已实现，以及是否存在可连接的协议传输。这可以防止在组合根可用之前，把一个可执行的传输中立接口描述成 MCP 服务器。

目录是索引，不是另一条执行路径。可执行行为仍以 TypeScript 领域和应用代码为权威，编码后的输入和输出仍以传输结构定义为权威。

## 状态含义

- `implemented` 表示所指明的传输及其生产所需的行为是可执行的。
- `partial` 标明确切的可执行层，同时列出缺失的生产层或传输层。
- `planned` 是经过评审的名称或契约，没有可执行的产品接口。
- `deprecated` 仅为迁移而保留在列表中。

仅由内存适配器支撑的应用用例是 `partial`，即使它的领域和应用测试通过也是如此。事件在业务事务把它写入真正的发件箱之前一直是 `planned`。文档中记载的 CloudLink 消息，只有在线路解码和所属的应用行为都可执行之后才算已实现。

## 命令治理

每个命令条目都声明权限、风险、确认、幂等性、到期和审计。缺少元数据意味着该命令不能开放。传输可以增加更严格的策略，但不能削弱目录中的治理。

查询声明一项权限，并且绝不改变产品状态。源自边缘端、会改变投影的观测属于命令，即使它描述的是事实而不是请求物理动作。

## 集成发现契约

`integration.projection.list` 是一个独立的只读应用端口和查询；它不是投影写入存储库上的方法。它与精确查询 `integration.projection.get` 使用同一个 `integration.projection.read` 权限。列表输入是封闭的，只接受可选的网关身份、不透明游标和有界的条数上限。

结果按网关身份、再按集成身份稳定排序。除这些身份之外，它只包含集成种类、快照代次、实体数和最新观测数、接收时间以及修订版。提供方载荷、任意拓扑数据、来源地址和机密都不在目录契约之内。列表结果和详情结果都是边缘端上报的副本，不是实时的物理真相。

内存适配器和 PostgreSQL 适配器都实现了该目录。PostgreSQL 查询使用租户行级安全、显式的租户／项目参数、可选的网关过滤、键集分页，并多取一行来判断是否存在下一页。可选的 MCP 目录和详情资源适配器会调用这些应用查询，但目前还不存在可连接的 MCP 传输。

## 兼容性

`schema_version` 会在目录结构发生不兼容更改之前变更。能力名称、错误代码、事件名称和操作标识符在一个版本内保持稳定。只有当旧的读取方可以安全地忽略新增字段时，添加字段才是向后兼容的。

目录目前记载了两个公开的元数据操作、五个经过身份验证的机群操作、一个以令牌授权的 AetherEdge 认领操作，以及两个经过身份验证的审计查询操作（JSON 和有限的 SSE 快照）；部分实现的提供商、计划、登记、CloudLink 会话、运行时清单、遥测、告警、制品注册表、部署、受治理作业、Webhook 和数据导出应用切片；以及规划中的后续物联网产品能力。网关注册和登记声明的签发／消费已完成生产组合，因为 PostgreSQL 适配器把每次状态转换与审计和发件箱状态写在同一个事务中。认领只绑定经过校验的 Ed25519 凭据请求指纹；活动凭据签发和 CloudLink 身份验证仍是单独的规划中能力。集成投影和默认关闭的集成控制切片现在指明了各自的事务性 PostgreSQL 账本，包括真实数据库上的并发、回滚、重启和行隔离证据。这并不意味着它们的生产组合、签名密钥生命周期、公开的智能体、真实消息代理的资格认定或 MCP 线路服务器已经存在。目录还把实验性的 CloudLink MQTT 层与生产组合和 AetherEdge 联合一致性分开命名。部分实现的 `cloudlink.session.challenge.request` 和 `cloudlink.session.gateway-signed.accept` 条目描述可执行的 v1alpha1 质询／hello 路径及其内存、PostgreSQL、Node.js Ed25519 和 MQTT 层。它们不声称具备生产身份验证：原子的凭据／密钥生命周期、持久的命令审计和逐条上行消息的网关签名身份验证都还缺失，因此之后的业务上行消息会以失败关闭方式被拒绝。已部署的 PostgreSQL 机群和审计组合并不意味着存在生产实时事件流、外部 Webhook 发送方、导出工作进程／下载接口、生产 CloudLink 进程、完整的迁移编排或租户成员关系管理。已部署的 HTTP 审计路由确实会验证 Supabase Auth ES256 访问令牌，并且只接受来自管理员控制的 `app_metadata` 的授权范围；这并没有实现其余的 IAM 生命周期。
